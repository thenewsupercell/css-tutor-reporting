# LVAEP Tutor Reporting

A focused replacement for the paper workflow used by LVAEP’s tutoring program. Tutors record each session once; staff can then review current activity, track student goals, and export monthly totals without re-entering data.

This project was built as a Columbia Software Solutions take-home. It favors a complete, understandable workflow over broad administrative features.

## Product approach

The legacy form uses a July–June grid of days and months. That layout is useful on paper, but it makes each session harder to validate, summarize, and reuse. This app stores individual sessions—with a student, date, duration, and optional notes—and derives dashboard totals, monthly reports, and CSV exports from those records.

Key decisions:

- Keep session entry short and show only the demo tutor’s active assignments.
- Derive reports from sessions instead of storing separate monthly report records.
- Preserve historical assignments so old sessions remain tied to the correct tutor and student.
- Keep correction lightweight: recent sessions can be deleted from the dashboard after confirmation.
- Use one shared Supabase dataset while isolating persistence behind a repository and store boundary.

## Features

- Responsive dashboard with current-month totals and recent activity
- Accessible session form with duration shortcuts and inline validation
- Student assignment overview and persistent goal completion tracking
- Monthly tutor/student summaries with client-side CSV export
- Supabase persistence with explicit Row Level Security policies and least-privilege grants
- Loading, empty, success, and error states for the main workflows

## Stack and architecture

- Next.js App Router, React, and TypeScript
- Tailwind CSS
- Supabase Postgres and `@supabase/supabase-js`
- Vercel-ready deployment configuration
- Node’s built-in test runner for focused report aggregation tests

The client-side data provider exposes a small external store. The store calls a Supabase repository for loading data, creating or deleting sessions, and toggling goal completion. UI components use the domain types in `src/lib/types.ts`; reports and CSV output are generated by the pure helpers in `src/lib/report-aggregation.ts`.

The database contains `tutors`, `students`, `assignments`, `sessions`, and `goals`. Sessions reference assignments, which preserves the tutor/student relationship that existed when the session occurred. Duration is stored as integer minutes and the session date as a PostgreSQL `date`.

## Local setup

Prerequisites: Node.js 20+ and a Supabase project.

1. Install dependencies:

   ```bash
   npm install
   ```

2. Copy the environment template and add the values from the Supabase project’s **Connect** dialog or **Settings → API Keys**:

   ```bash
   cp .env.example .env.local
   ```

   ```bash
   NEXT_PUBLIC_SUPABASE_URL=https://your-project-ref.supabase.co
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your_key
   ```

3. In the Supabase SQL Editor, run every file in `supabase/migrations` once, in filename order:

   1. `20260921000000_create_tutoring_schema.sql`
   2. `20260922000000_enable_goal_status_updates.sql`
   3. `20260923000000_secure_public_demo_with_rls.sql`

   Then run `supabase/seed.sql` once. Its inserts are idempotent, so rerunning it will not duplicate the fictional records. Existing projects only need migrations they have not already applied.

4. Start the app:

   ```bash
   npm run dev
   ```

For Vercel, add the same two public environment variables to the project before deploying. Never expose a Supabase secret or service-role key in a `NEXT_PUBLIC_` variable.

## Scope and security

This is intentionally an unauthenticated demo using fictional data. RLS allows anonymous users to read the demo dataset, create and delete sessions, and update only `status` and `completed_at` on goals. Because every visitor has the same anonymous role, actions cannot be attributed to a person and any visitor can perform those allowed operations.

The take-home omits user accounts, roles, student or assignment creation, tutor management, and full record editing. For production, I would add Supabase Auth, organization and role membership, tutor-scoped policies, audit history or soft deletion, server-side validation, monitoring, and end-to-end tests for the primary workflows.
